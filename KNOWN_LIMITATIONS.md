# Known Limitations

Honest inventory of what is real vs. simulated, as of this build. Nothing below should be read as "done" unless explicitly marked real/working.

## Automated testing — real, passing

- `npm test`: 39 unit tests, no database. `npm run test:integration`: 11 tests driving a real `next dev` server + real Postgres purely over HTTP — auth lifecycle, tenant isolation, RBAC via a real invite-acceptance flow, and entitlement blocking. See `TEST_PLAN.md` for the full breakdown.
- This suite already found and fixed two real issues rather than just confirming assumptions: the signup rate limit (10/hour/IP) was tight enough to trip during automated testing itself — and would plausibly trip for real users behind a shared office/university IP — raised to 30/hour. And a draft RBAC test incorrectly expected an invite to succeed on an already-full FREE-plan tenant; the app's 402 was correct, the test was wrong and got fixed.
- The local `prisma dev` ephemeral Postgres became unstable under this session's very heavy cumulative use (many schema pushes and test runs against one long-lived process) — resolved every time by recreating it (`prisma dev rm` + `prisma dev --detach` + re-push schema). This is a quirk of that lightweight dev-only tool, not the application, and not expected against a real Postgres (see `TEST_PLAN.md` for detail).
- `.github/workflows/ci.yml` now runs `test:integration` too, in a separate `integration` job against a real `postgres:16-alpine` service container, migrated via `npx prisma migrate deploy` (the real production command — confirmed locally that it applies all 4 migrations cleanly to a genuinely empty database, not just via `db push`). Neither CI job has actually executed in GitHub yet.
- Wiring up CI surfaced a real, separate bug: `npm ci` (a clean install, no local `--legacy-peer-deps` override) failed with `ERESOLVE` because `@types/node@^20` conflicted with `vitest@5`'s peer requirement (`^22 || >=24`) — reproduced by running `npm ci` from scratch, then fixed by bumping to `@types/node@^22` to match the Node 22 this app already targets everywhere else (Dockerfile, CI). This would have broken CI's very first run had it not been caught here.
- `npm run test:e2e`: 27 Playwright tests against a real Chromium browser + real `next dev` server + real Postgres — full user-facing flows (signup, login, logout, keyword research, rank tracking, site audit, CRM, team entitlements), a broken-link/broken-image sweep across every public and dashboard route, and an `@axe-core/playwright` WCAG 2.2 AA accessibility scan. **Building this suite found a real bug, not a test artifact**: Next.js's dev-mode route indicator (bottom-left by default) physically overlapped the dashboard sidebar's "Log out" button and intercepted real mouse clicks there — confirmed by reproducing it with an actual coordinate-based click in a live browser (it did nothing) versus a JS-dispatched click on the same element (it worked), proving the browser's real hit-testing was routing clicks to the overlay. Fixed via `devIndicators: false` in `next.config.ts`; compile/runtime errors still surface without it per Next's own docs. This was dev-mode-only (not a `next start`/production defect), but it would have quietly broken local dev/QA testing of a core flow — worth having caught. See `TEST_PLAN.md` for the full breakdown.
- Fixing that also surfaced a second, independent real bug: **every form label in the app was visually associated with its input but not programmatically** (`<label>` with no `htmlFor`/`id` pairing) — a real WCAG 2.2 AA violation (this spec explicitly requires "Proper labels"), not just a testing inconvenience. `getByLabel()`-based Playwright locators correctly failed to find these inputs, which is exactly what a screen reader's accessible-name computation would also fail at. Fixed across all 8 affected forms (signup, login, forgot-password, reset-password, invite-accept, team invite, CRM create-company, rank-tracking) by wiring `useId()`-generated ids through `htmlFor`/`id` pairs.
- Adding the axe-core accessibility spec found a third, independent, and genuinely widespread real bug: **bare `text-slate-400` (i.e. not `dark:`-prefixed) computed to a 2.63:1 contrast ratio on white backgrounds**, failing WCAG AA's 4.5:1 minimum for normal text — flagged on every route axe checked. This turned out to be used across 26 files (table headers, footer links, form dividers/hints, empty states, timestamps). Fixed by changing every bare occurrence to `text-slate-500` (#64748b), hand-verified via the WCAG relative-luminance formula to give ~4.77:1 against white, before applying it everywhere — `dark:text-slate-400` pairs were left untouched since dark backgrounds already contrast fine against slate-400. All 6 accessibility tests pass after the fix.

## SEO engine

- **Site auditor: real.** Crawls actual pages via `fetch`, parses real HTML with `cheerio`. Verified against `example.com`. Results now persist to `SiteAuditRun`/`SiteAuditIssue`, scoped to the authenticated tenant's project.
- **Keyword metrics (volume/difficulty/CPC): mocked.** No paid data provider (DataForSEO, Ahrefs API, Google Keyword Planner, etc.) is connected. `src/lib/seo/providers/mock.ts` returns deterministic fake numbers. Swapping to real data requires: an account with a provider, its credentials in `.env`, and implementing the corresponding adapter (the factory in `providers/index.ts` will throw a clear error if credentials are set but the adapter isn't implemented — it will never silently return fake data as if real). Results persist to `Keyword` rows, scoped to the tenant's general project.
- **Rank tracking: mocked**, same reasoning — needs a SERP data provider (SerpApi, DataForSEO SERP API, etc.). Results persist to `RankSnapshot` rows.
- **AI-search visibility (AI Overviews / ChatGPT Search / Perplexity citations): mocked.** No provider currently offers a clean API for this; would likely require a custom scraping/monitoring pipeline, which has real ToS and reliability risk to design carefully before building. Not persisted yet (no UI calls this provider).

## Auth & tenancy — real, working

- **Email/password signup and login: real.** bcrypt password hashing (cost 12), opaque session tokens (32 random bytes, only the SHA-256 hash stored server-side so a DB read alone can't impersonate a session), httpOnly/secure/sameSite=lax cookies, 30-day expiry, explicit revocation on logout. Verified end-to-end in-browser: signup creates a real tenant + OWNER membership + hashed password in Postgres; logout revokes the session and the dashboard correctly redirects to `/login` afterward.
- **Tenant isolation**: every SEO engine API route now requires a valid session and scopes all reads/writes to the caller's tenant via `getCurrentTenantContext()`. No route accepts a tenant/project ID from the client — it's always derived server-side from the session.
- **Team invitations and RBAC enforcement: real.** ADMIN+ can invite by email/role, revoke pending invitations, change roles, deactivate/reactivate, and remove members (`/team`, `src/app/api/team/**`). Role checks are enforced server-side in every route via `requireRole()` — verified by calling `/api/team/invite` directly as a MEMBER and getting a 403, not just hiding the button in the UI. Last-owner protection is enforced (can't demote/deactivate/remove the only active OWNER). Invite acceptance creates the account (if new) + membership in one transaction and writes audit log entries (`invitation.created`, `invitation.accepted`) — confirmed via direct DB query.
- **Google/Microsoft OAuth: real protocol implementation, untested end-to-end.** `src/lib/auth/oauth/{google,microsoft}.ts` implement the standard OAuth 2.0 authorization-code flow (authorization URL, code-for-token exchange, userinfo fetch) with CSRF-safe state validation (random state stored in a short-lived httpOnly cookie, checked byte-for-byte on callback). Verified so far: with no `GOOGLE_CLIENT_ID`/`MICROSOFT_CLIENT_ID` set, hitting `/api/auth/oauth/google/start` or `.../microsoft/start` correctly returns a 501 explaining the provider isn't configured, rather than pretending to work. **The actual provider round-trip (redirect to Google/Microsoft, consent, callback, account creation) has NOT been tested, because that requires a real Google Cloud OAuth client and Azure App Registration, which this environment doesn't have.** Once you create those and set the env vars, this needs a real manual test before you trust it in production.
- **What's still missing**: "remember this device"/MFA, multi-tenant switching for a user who belongs to more than one tenant (v1 assumes one primary tenant per user).

## Transactional email (Resend) — real, verified

- `src/lib/email/resend.ts` wraps the real Resend SDK behind `sendEmail()`, which returns `{ sent: false }` rather than throwing when `RESEND_API_KEY`/`EMAIL_FROM` aren't set — every caller (signup verification, password reset, team invites) falls back gracefully instead of crashing or silently pretending to have sent something.
- **Email verification**: signup now creates an `EmailVerificationToken` and attempts to send a verification email. Unverified users see a dismissable-by-completing banner in the dashboard with a "Resend verification email" button. Verified end-to-end **against real DB rows, with no Resend key configured**: signup created a real token, `GET /api/auth/verify-email/[token]` correctly redirected to `/keywords?verified=1` and set `user.emailVerified` in Postgres, and the resend button worked. OAuth signups set `emailVerified` immediately (the provider already verified it) — only password signups need this flow.
- **Forgot/reset password**: `/forgot-password` always shows the same confirmation regardless of whether the email exists (no enumeration); `/reset-password/[token]` validates the token, enforces the password strength rule, and — importantly — **revokes every existing session for that user** on a successful reset (a reset implies the account may have been compromised). Verified end-to-end: requested a reset, pulled the token from the DB (since no email was sent without a Resend key), set a new password, confirmed the new password logs in and the old one is rejected.
- **Team invites**: `/api/team/invite` now attempts to send the invite via email; if that fails or Resend isn't configured, it falls back to returning the invite link in the response for manual sharing, exactly as before — the UI shows either "Invitation email sent." or the raw link, never both silently swapped.
- **Not tested**: the actual Resend API call succeeding (this environment has no `RESEND_API_KEY`) — only the unconfigured/fallback path is verified. Get a real Resend API key and verified sending domain before trusting delivery in production.

## Billing — real Stripe integration code, untested end-to-end

- `src/lib/billing/stripe.ts` wraps the real Stripe SDK (checkout sessions, billing portal sessions, webhook signature verification via `stripe.webhooks.constructEvent`). `src/app/api/billing/{checkout,portal,webhook}/route.ts` implement subscribe, manage-billing, and event-handling flows. Webhook processing is idempotent (skips a `stripeEventId` it's already recorded in `BillingEvent`) and maps `checkout.session.completed` / `customer.subscription.updated` / `customer.subscription.deleted` to the tenant's plan, billing interval, period end, and status.
- **Verified**: with no `STRIPE_SECRET_KEY` set, `/api/billing/checkout`, `/api/billing/portal`, and `/api/billing/webhook` all return a clear 501 rather than pretending to work — checked directly via curl and through the `/billing` UI (clicking "Upgrade" surfaces the real error text, not a generic failure).
- **NOT verified**: the actual Stripe round-trip (real checkout session redirect, webhook delivery, subscription lifecycle) — this environment has no Stripe test-mode API key. Needs a real manual test against Stripe test mode before trusting it in production, including webhook signature verification against Stripe's actual signing secret (only the "missing secret" path has been exercised, not a real signed payload).
- **Pricing is a proposal**, not something charged to any real customer: Free/Starter ($49/mo)/Growth ($129/mo)/Scale ($349/mo)/Enterprise (custom), defined in `src/lib/billing/plans.ts`. Adjust before connecting a live Stripe account.
- **Entitlement enforcement: real, verified.** `src/lib/billing/entitlements.ts` checks team-member count and monthly audit count against the tenant's plan limits *before* allowing the action — not just displayed as a table. Verified in-browser: on the FREE plan (1 team member max), a second invite attempt is blocked with a 402 and the specific message ("Your Free plan allows up to 1 team member(s)..."), both via direct API call and through the `/team` UI. Project-count and per-plan keyword-count limits are defined but not yet enforced anywhere (no route creates unlimited projects/keywords today in a way that would exceed them).

## Super admin — real, verified

- `/admin` shows aggregate platform metrics (tenant/user counts, active/trialing/suspended counts) and a tenant list with plan, status, member/project counts, and billing-connection state — deliberately **no tenant business data** (no keywords, audit results, or CRM content), per the spec's "must not casually expose tenant-sensitive data" requirement.
- `/admin/tenants/[id]` shows one tenant's members (name/email/role/status) and its account-level audit log (e.g. `tenant.created`, `invitation.accepted`) — not its SEO/business data.
- **Suspending a tenant is a real, enforced control, not cosmetic.** Verified end-to-end: a super admin suspends a tenant via the API → the tenant's own dashboard immediately shows a "Workspace suspended" screen instead of the app → a direct call to `/api/seo/audit` from that tenant returns a 403 with the suspension message, confirmed independently of the UI. Reactivating restores access, also verified.
- There is deliberately **no self-service way to become a super admin** — `scripts/promote-super-admin.ts` requires direct database/environment access to run. This is intentional least-privilege, not an oversight.
- `/admin` and its API routes require `user.isSuperAdmin`, checked server-side (`requireSuperAdmin()` in every route, `AdminLayout` server component for the UI) — verified a non-admin request to `/api/admin/tenants` gets a 403.

## Security

- CSRF: relies on `sameSite=lax` cookies + the fact that all mutating routes are same-origin fetches from the dashboard; no explicit CSRF token yet. Acceptable for now but should be revisited once external integrations (webhooks, browser extensions) are added.
- Rate limiting is **in-memory, per-process** (`src/lib/auth/rate-limit.ts`) — fine for a single dev instance, but will not correctly limit abuse across multiple app instances/load balancers. Needs a shared store (Redis) before horizontal scaling.
- Login/signup responses are deliberately generic ("Invalid email or password" / "Could not create account with these details") to avoid user enumeration.
- Baseline security headers (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, a restrictive `Permissions-Policy`) are configured in `next.config.ts` and verified via `curl -i`. No CSP yet — deliberately deferred until it can be tuned against Stripe Checkout and OAuth redirects rather than added speculatively.
- No email verification means anyone can sign up with an email they don't own; nothing currently depends on `emailVerified` being true, so this isn't exploitable yet, but should be closed before allowing any workflow that trusts email ownership (e.g. team invitations by email).

## Testing

See "Automated testing" above and `TEST_PLAN.md` for the full unit/integration/E2E/accessibility suite (77 automated tests total). The manual smoke tests below were performed in-browser during development, against a real local Postgres instance (via `prisma dev`, not Docker — Docker isn't available in this environment), and are now largely superseded by the automated suites above — kept here as a record of what was directly verified:
- Signup creates a tenant, OWNER membership, and bcrypt-hashed password (confirmed via direct DB query, not just API response)
- Keyword research and rank tracking persist rows scoped to the tenant's project (confirmed via direct DB query)
- Site audit runs a real crawl and returns correct issues
- Logout revokes the session; the protected dashboard correctly bounces back to `/login` afterward
- Unauthenticated requests to `/keywords`, `/rankings`, `/audit`, `/team` are redirected to `/login` by middleware
- Full invite lifecycle tested: OWNER invites a new email → invite link works for an unauthenticated visitor → accepting creates the account, membership, and audit log rows → the new MEMBER sees no management controls in `/team` and gets a 403 calling `/api/team/invite` directly
- Billing entitlement enforcement tested: FREE-plan tenant blocked from adding a 2nd team member with the correct 402 + message, both via API and UI
- Unconfigured-provider paths tested for OAuth and Stripe: all six routes (`google`/`microsoft` × start, `billing` checkout/portal/webhook) return clear 501s instead of crashing or silently no-op'ing
- `npm run build` (production build, `output: "standalone"`) succeeds, and the resulting `.next/standalone/server.js` was run directly (not inside Docker — no Docker in this environment) against the real local Postgres: `/api/auth/me` returned a genuine DB-backed response and `/audit` correctly redirected when unauthenticated, confirming the generated Prisma client bundles correctly into the standalone output. **The `Dockerfile` itself has not been built or run** (no Docker available here) — the underlying Next.js artifacts it packages are verified working, but the actual `docker build`/`docker compose up` has not been executed. Do this once before relying on it for a real deployment.

## Infrastructure

No load testing, no penetration testing, no CI/CD, no staging/production environment has been provisioned. Domain availability for proposed brand names has NOT been verified — check with a registrar before committing to a name. Local dev database is Prisma's built-in `prisma dev` server (no Docker available in this environment) — production should use a real managed or self-hosted Postgres instance, not this dev server.

## Dependencies

`prisma`'s transitive dependencies (`mysql2`, `deepmerge-ts`) currently carry 2 unpatched high-severity advisories upstream (checked 2026-09-17). Not currently exploitable in this app (Postgres-only, no user-controlled recursive config merging), but should be re-checked (`npm audit`) before production deployment in case a patched Prisma release is available by then.
